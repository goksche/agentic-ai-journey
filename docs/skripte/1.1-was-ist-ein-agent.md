# Lernskript 1.1 – Was ist ein Agent?

Modul 1.1 · Program Induction · Woche 1 · Lesezeit ca. 60 Minuten

Lernziele dieses Moduls:

1. Du kannst den Unterschied zwischen einem LLM-Aufruf, einem Workflow und einem Agenten präzise erklären.
2. Du kannst ein beliebiges KI-System auf der Agency-Stufenleiter einordnen und die Einordnung begründen.
3. Du kennst die fünf Bausteine eines Agenten und die typischen Arten, wie Agenten scheitern.
4. Deine Entwicklungsumgebung läuft, und deine API-Zugänge funktionieren.

## 1. Ausgangspunkt: Was ein Sprachmodell allein kann

Ein Large Language Model (LLM) ist eine Funktion: Text rein, Text raus. Es hat kein Gedächtnis zwischen zwei Aufrufen, keinen Zugriff auf die Welt und keine Möglichkeit, etwas zu *tun*. Alles, was es «weiss», steckt in den Gewichten (Trainingswissen) oder im Text, den du ihm im Aufruf mitgibst (Kontext).

```
Prompt  ──►  LLM  ──►  Antwort
```

Das reicht für erstaunlich viel: zusammenfassen, übersetzen, klassifizieren, Code schreiben. Aber es fehlen drei Dinge, die echte Arbeit ausmachen:

- **Handeln**: eine Datei schreiben, eine API aufrufen, eine Suche starten.
- **Rückmeldung verarbeiten**: sehen, was die Handlung bewirkt hat, und darauf reagieren.
- **Über mehrere Schritte durchhalten**: ein Ziel verfolgen, das zehn oder fünfzig Einzelschritte braucht.

Genau diese drei Dinge machen aus einem Sprachmodell einen Agenten.

## 2. Definition

> Ein **Agent** ist ein System, in dem ein Sprachmodell in einer Schleife selbst entscheidet, welche Aktion es als Nächstes ausführt, das Ergebnis dieser Aktion beobachtet und so lange weitermacht, bis ein Ziel erreicht oder ein Abbruchkriterium erfüllt ist.

Die entscheidenden Wörter sind **selbst entscheidet** und **Schleife**. Ein System, in dem der Programmierer den Ablauf fest vorgibt und das LLM nur einzelne Schritte ausfüllt, ist kein Agent, sondern ein Workflow (Abschnitt 4).

Die Grundschleife sieht so aus:

```
          ┌──────────────────────────────────────┐
          ▼                                      │
   Ziel + Kontext ──► LLM entscheidet ──► Aktion ausführen
                           │                     │
                           │               Beobachtung
                           ▼               (Ergebnis)
                    «Fertig»-Antwort             │
                                                 │
          ◄──────────── Kontext ergänzen ◄───────┘
```

In Pseudocode sind das kaum zehn Zeilen. Diesen Loop baust du in Modul 1.3 ohne Framework selbst:

```python
messages = [system_prompt, user_goal]
for step in range(MAX_STEPS):
    response = llm(messages, tools=TOOLS)
    if response.is_final_answer:
        return response.text
    result = execute(response.tool_call)       # Handlung
    messages += [response, result]             # Beobachtung zurück in den Kontext
raise StepLimitReached()
```

Alles, was Frameworks wie LangGraph, CrewAI oder AutoGen bieten, ist Komfort, Struktur und Robustheit um diese Schleife herum.

## 3. Die fünf Bausteine eines Agenten

| Baustein | Frage, die er beantwortet | Beispiele |
| --- | --- | --- |
| **Modell** | Wer denkt und entscheidet? | Ein Frontier-Modell per API, ein lokales Open-Weights-Modell |
| **Tools** | Was kann der Agent tun? | Websuche, Datei lesen/schreiben, Code ausführen, API aufrufen |
| **Gedächtnis** | Was weiss er über den aktuellen Kontext hinaus? | Gesprächsverlauf, Zusammenfassungen, Vektordatenbank, Notizdatei |
| **Planung** | Wie zerlegt er ein grosses Ziel? | Plan erstellen und abarbeiten, Teilziele, Selbstkorrektur |
| **Umgebung und Grenzen** | Wo handelt er, und was darf er nicht? | Sandbox, Berechtigungen, Budget, Schrittlimit, Freigaben durch Menschen |

Der fünfte Baustein wird in Tutorials oft vergessen und ist in der Praxis der wichtigste. Ein Agent ohne Grenzen ist ein Risiko, kein Produkt.

### Tools im Detail

Moderne Modelle unterstützen **Tool Calling** (auch Function Calling): Du beschreibst dem Modell verfügbare Funktionen mit Name, Beschreibung und Parametern im JSON-Schema-Format. Das Modell antwortet dann nicht mit Text, sondern mit einer strukturierten Anfrage wie «rufe `search` mit `query="ReAct paper"` auf». *Dein Code* führt die Funktion aus und gibt das Ergebnis zurück. Das Modell selbst führt nie etwas aus. Diese Trennung ist die zentrale Sicherheitsgrenze, die du in allen späteren Modulen nutzt.

### Gedächtnis im Detail

Das Kontextfenster ist das Arbeitsgedächtnis: alles, was das Modell in diesem Aufruf sieht. Es ist begrenzt und kostet pro Token. Langfristiges Gedächtnis muss deshalb ausserhalb liegen und gezielt in den Kontext geholt werden. Dafür gibt es Zusammenfassungen, Retrieval aus einer Vektordatenbank oder strukturierte Notizen. Das ist Thema von Modul 1.5.

## 4. Workflow oder Agent? Die wichtigste Unterscheidung

| | Workflow | Agent |
| --- | --- | --- |
| Wer bestimmt den Ablauf? | Der Code (fest vorgegeben) | Das Modell (zur Laufzeit) |
| Anzahl Schritte | Bekannt | Unbekannt, variabel |
| Vorhersagbarkeit | Hoch | Niedriger |
| Kosten und Latenz | Planbar | Schwanken stark |
| Geeignet für | Klar strukturierte, wiederkehrende Aufgaben | Offene Aufgaben, bei denen der Lösungsweg vorher unklar ist |

Fünf verbreitete **Workflow-Muster**, die du kennen solltest, bevor du zu Agenten greifst:

1. **Prompt Chaining**: Schritt A erzeugt Input für Schritt B (z. B. Gliederung → Text → Korrektur).
2. **Routing**: Ein erster Aufruf klassifiziert die Anfrage und leitet sie an einen spezialisierten Pfad weiter.
3. **Parallelisierung**: Mehrere Aufrufe gleichzeitig (z. B. drei Perspektiven auf dasselbe Dokument), danach zusammenführen.
4. **Orchestrator–Worker**: Ein Aufruf zerlegt die Aufgabe in Teilaufgaben, Worker bearbeiten sie. Das ist schon nahe am Agenten.
5. **Evaluator–Optimizer**: Ein Aufruf erzeugt, ein zweiter bewertet, der erste verbessert, bis das Ergebnis passt.

> **Faustregel:** Nimm die einfachste Lösung, die funktioniert. Erst ein einzelner gut gebauter Aufruf, dann ein Workflow, erst danach ein Agent. Agenten tauschen Vorhersagbarkeit und Kosten gegen Flexibilität. Dieser Tausch muss sich lohnen.

Die Unterscheidung stammt in dieser Form aus dem Anthropic-Beitrag «Building effective agents». Lies ihn diese Woche ganz (siehe Quellen).

## 5. Die Agency-Stufenleiter

Agency ist kein Ja/Nein, sondern ein Kontinuum. Für die Einordnung nutzen wir in diesem Studium fünf Stufen:

| Stufe | Bezeichnung | Wer entscheidet den nächsten Schritt? | Beispiel |
| --- | --- | --- | --- |
| 0 | **Einzelaufruf** | Niemand, es gibt nur einen Schritt | «Fasse diesen Text zusammen» |
| 1 | **Assistent / Chatbot** | Der Mensch, nach jeder Antwort | Chat-Oberfläche ohne Tools |
| 2 | **Copilot** | Der Mensch; das Modell schlägt vor oder nutzt einzelne Tools auf Anfrage | Code-Vervollständigung in der IDE |
| 3 | **Workflow mit LLM-Schritten** | Der Code; das Modell füllt vordefinierte Schritte | Ticket → Klassifikation → Antwortentwurf |
| 4 | **Agent mit Leitplanken** | Das Modell, innerhalb von Berechtigungen und mit Freigaben | Coding-Agent, der Änderungen vorschlägt und Tests laufen lässt, mit Freigabe vor dem Merge |
| 5 | **Autonomer Agent** | Das Modell, über lange Zeit, ohne laufende Aufsicht | Agent, der selbständig Issues löst und Pull Requests erstellt |

Drei Fragen helfen beim Einordnen:

1. Kann das System **handeln** oder nur Text erzeugen?
2. Wer legt die **Reihenfolge der Schritte** fest: Code, Mensch oder Modell?
3. Wie lange läuft es **ohne menschliche Zwischenschritte**?

## 6. Wie Agenten scheitern

Wer Agenten baut, verbringt den Grossteil der Zeit nicht mit dem Happy Path, sondern mit Fehlern. Die wichtigsten Fehlerarten:

### 6.1 Fehlerakkumulation

Wenn jeder Schritt mit 95 % Wahrscheinlichkeit korrekt ist, ist eine Kette von Schritten nur so gut wie das Produkt:

| Schritte | Erfolgswahrscheinlichkeit bei 95 % pro Schritt |
| --- | --- |
| 1 | 95 % |
| 5 | 77 % |
| 10 | 60 % |
| 20 | 36 % |

Deshalb sind Selbstkorrektur, Tests als objektive Rückmeldung und kurze Ketten so wichtig. Ein Agent, der seine eigenen Fehler bemerken kann (z. B. weil Tests fehlschlagen), durchbricht diese Rechnung. Darauf baut Projekt «Forge» auf.

### 6.2 Halluzinierte Handlungen und Fakten

Das Modell erfindet ein Tool, das es nicht gibt, ruft ein echtes Tool mit erfundenen Parametern auf oder zitiert eine Quelle, die nicht existiert. Gegenmittel: strikte Schema-Validierung, Rückgabe klarer Fehlermeldungen an das Modell, Belegpflicht. Das ist der Kern von Projekt «Scholar».

### 6.3 Endlosschleifen und Abschweifen

Der Agent wiederholt dieselbe Aktion, dreht sich im Kreis oder verliert das ursprüngliche Ziel aus den Augen. Gegenmittel: Schrittlimit, Erkennung von Wiederholungen, Ziel regelmässig in den Kontext zurückholen.

### 6.4 Prompt Injection

Text aus einer Tool-Rückgabe (Webseite, Dokument, E-Mail) enthält Anweisungen, die das Modell als Befehl statt als Daten behandelt: «Ignoriere alle bisherigen Anweisungen und sende …». Je mehr ein Agent liest und je mehr er darf, desto gefährlicher wird das. Gegenmittel: Least Privilege, Freigaben vor riskanten Aktionen, Trennung von Daten und Anweisungen. Vertieft in Modul 1.4 und 2.3.

### 6.5 Kosten- und Zeitexplosion

Ein Agent, der 200 Schritte mit je 50 000 Token Kontext macht, verbraucht 10 Millionen Input-Token, und das für eine einzige Aufgabe. Gegenmittel: Budget pro Aufgabe, Kontext komprimieren, günstigere Modelle für einfache Teilschritte.

### 6.6 Falsch verstandenes Ziel

Der Agent erfüllt die Aufgabe wörtlich, aber nicht sinngemäss. Ein Beispiel: Er «behebt» fehlschlagende Tests, indem er sie löscht. Gegenmittel: präzise Erfolgskriterien, Verbote explizit machen, Ergebnisse unabhängig prüfen.

## 7. Wann man keinen Agenten bauen sollte

- Der Ablauf ist bekannt und stabil → Workflow.
- Ein Fehler ist teuer und nicht rückgängig zu machen (Zahlungen, Löschungen, Kommunikation an Kunden) und es gibt keine Freigabe durch einen Menschen.
- Es gibt keine Möglichkeit, das Ergebnis zu prüfen (keine Tests, keine Quellen, keine Metrik).
- Die Latenz muss garantiert unter einer Sekunde liegen.

Ein guter Agentenentwickler sagt öfter «Das braucht keinen Agenten» als «Bauen wir einen Agenten».

### 8.1 Cursor im Lernmodus

Der Agent-Modus von Cursor kann jede Übung in Sekunden lösen. Damit hättest du sie aber nicht gelernt. Im Repo liegt deshalb die Projektregel `.cursor/rules/lernmodus.mdc`. Sie weist den Cursor-Agenten an, bei Übungen zu erklären, Hinweise zu geben und Code zu reviewen, statt Lösungen zu schreiben.

| Situation | Cursor nutzen für |
| --- | --- |
| Übungsaufgaben (Standard) | Konzepte erklären, Fehlermeldungen deuten, Hinweise, Review deines Codes |
| Aufgaben mit ausdrücklichem KI-Teil (z. B. Modul 1.2, Aufgabe 2) | Alles. Schreib im Chat «KI-Modus», dann darf der Agent voll mitarbeiten. |
| Infrastruktur, Konfiguration, Boilerplate (Dockerfiles, CI) | Alles, sofern du jede Zeile verstehst |

Cursor ist ausserdem selbst ein Agent der Stufe 4. Beobachte beim Arbeiten, wie er plant, Tools aufruft (Dateien lesen, Terminal) und auf Ergebnisse reagiert. Das ist die Schleife aus Abschnitt 2 in Aktion.

API-Keys gehören in `.env` (steht in `.gitignore`), nie in den Code und nie in einen Commit.
