## 1. Warum genau diese Themen?

Ein Agent ist zum grössten Teil gewöhnlicher Code um ein Sprachmodell herum. Vier Dinge kommen dabei ständig vor:

| Was der Agent tut | Was du dafür brauchst | Abschnitt |
| --- | --- | --- |
| Er bekommt JSON vom Modell zurück, etwa eine Tool-Anfrage, und muss prüfen, ob es stimmt | Typen und **Pydantic** | 2–3 |
| Er liest Dateien, ruft Programme auf, schreibt Ergebnisse | Dateien, Kontextmanager, Logging | 4 |
| Er muss zuverlässig funktionieren, auch nach Änderungen | **pytest** | 5 |
| Er ruft mehrere Tools gleichzeitig auf, z. B. fünf Websuchen | **async**/`await` | 7 |

Wer diese vier Dinge beherrscht, versteht später auch, was LangGraph, CrewAI oder das MCP-SDK unter der Haube tun.

## 2. Typangaben

Python prüft Typen zur Laufzeit nicht, aber Typangaben (Type Hints) machen Code lesbarer, helfen dem Editor und, wichtig für uns, lassen sich in Schemas für Sprachmodelle umwandeln.

```python
from datetime import datetime

def count_errors(statuses: list[int], threshold: int = 400) -> int:
    return sum(1 for s in statuses if s >= threshold)

def last_seen(entries: dict[str, datetime], ip: str) -> datetime | None:
    return entries.get(ip)
```

Die wichtigsten Schreibweisen ab Python 3.10:

| Schreibweise | Bedeutung |
| --- | --- |
| `list[str]`, `dict[str, int]`, `tuple[int, str]` | Container mit Elementtyp |
| `str \| None` | Text oder nichts (früher `Optional[str]`) |
| `Literal["GET", "POST"]` | nur genau diese Werte (aus `typing`) |
| `-> None` | Funktion gibt nichts zurück |

> **Merksatz:** Typangaben sind Dokumentation, die der Editor versteht. Geprüft werden sie erst durch ein Werkzeug wie Pydantic (zur Laufzeit) oder einen Type-Checker (vor der Ausführung).

## 3. Pydantic: Daten prüfen statt hoffen

Pydantic nimmt eine Klasse mit Typangaben und macht daraus einen **Prüfer**. Kommen Daten herein, egal ob aus einer Datei, einer API oder vom Sprachmodell, werden sie umgewandelt und geprüft. Stimmt etwas nicht, gibt es einen klaren Fehler statt eines stillen Bugs drei Schritte später.

```python
from datetime import datetime
from typing import Literal
from pydantic import BaseModel, Field, ValidationError, field_validator

class Request(BaseModel):
    method: Literal["GET", "POST", "PUT", "DELETE"]
    path: str
    status: int = Field(ge=100, le=599)       # 100–599, sonst Fehler
    size: int = Field(ge=0)
    timestamp: datetime

    @field_validator("path")
    @classmethod
    def path_must_start_with_slash(cls, v: str) -> str:
        if not v.startswith("/"):
            raise ValueError("Pfad muss mit / beginnen")
        return v

r = Request(method="GET", path="/index.html", status="200", size=512,
            timestamp="2026-10-10T13:55:36+02:00")
print(r.status + 1)        # 201: der Text "200" wurde zu int umgewandelt

try:
    Request(method="FETCH", path="index", status=999, size=-1, timestamp="gestern")
except ValidationError as e:
    print(e.error_count())  # 5 Fehler, jeder mit Feld und Grund
```

Die Methoden, die du am häufigsten brauchst (Pydantic Version 2):

| Methode | Zweck |
| --- | --- |
| `Model(**daten)` oder `Model.model_validate(dict)` | prüfen und Objekt erzeugen |
| `obj.model_dump()` / `obj.model_dump(mode="json")` | zurück in ein dict, mit `mode="json"` JSON-tauglich (z. B. Datum als Text) |
| `obj.model_dump_json(indent=2)` | direkt als JSON-Text |
| `Model.model_json_schema()` | **JSON-Schema der Klasse** |

Die letzte Zeile ist der Grund, warum Pydantic in diesem Studium so wichtig ist: Beim Tool Calling beschreibst du dem Modell Werkzeuge mit einem JSON-Schema (Skript 1.1, Abschnitt 3). Mit Pydantic schreibst du eine Klasse und bekommst das Schema geschenkt. Und wenn das Modell antwortet, prüft dieselbe Klasse, ob die Antwort passt. Fast alle Agenten-Frameworks arbeiten so.

**Pydantic oder `dataclass`?** Eine `@dataclass` aus der Standardbibliothek ist ein einfacher Datenbehälter ohne Prüfung. Für interne Strukturen reicht sie. Sobald Daten von aussen kommen, nimmst du Pydantic.

## 4. Dateien, Kontextmanager, Logging

**Pfade** mit `pathlib` statt Textverkettung. Das funktioniert unter Windows und Linux gleich:

```python
from pathlib import Path

log_file = Path("data") / "access.log"
if not log_file.exists():
    raise SystemExit(f"Datei nicht gefunden: {log_file}")
```

**Kontextmanager** (`with`) sorgen dafür, dass eine Datei auch bei einem Fehler wieder geschlossen wird:

```python
with log_file.open(encoding="utf-8") as f:
    for line_no, line in enumerate(f, start=1):
        ...
```

Gib beim Öffnen immer `encoding="utf-8"` an. Unter Windows ist sonst eine andere Kodierung voreingestellt, und Umlaute gehen kaputt.

**Logging** statt `print`, sobald ein Programm mehr als ein Skript ist. Du kannst die Menge der Meldungen steuern, ohne Code zu ändern:

```python
import logging
log = logging.getLogger(__name__)
logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")

log.info("Lese %s", log_file)
log.warning("Zeile %d übersprungen: %s", line_no, grund)
```

Bei Agenten ist das später zentral: Jede Entscheidung und jeder Tool-Aufruf soll nachvollziehbar sein (Modul 3.1).

## 5. Testen mit pytest

Ein Test ist eine Funktion, deren Name mit `test_` beginnt, und die mit `assert` prüft, was herauskommen soll. pytest findet und startet alle Tests von selbst.

```python
# tests/test_counting.py
import pytest
from loglens.counting import count_errors

def test_counts_4xx_and_5xx():
    assert count_errors([200, 404, 500, 301]) == 2

@pytest.mark.parametrize("statuses, expected", [
    ([], 0),
    ([200, 200], 0),
    ([400], 1),
])
def test_edge_cases(statuses, expected):
    assert count_errors(statuses) == expected

def test_rejects_bad_input():
    with pytest.raises(TypeError):
        count_errors(None)
```

Drei Werkzeuge, die du in den Aufgaben brauchst:

| Werkzeug | Wofür |
| --- | --- |
| `@pytest.mark.parametrize` | dieselbe Prüfung mit vielen Eingaben |
| `pytest.raises(Fehler)` | prüfen, dass ein Fehler *kommt* |
| `tmp_path` (als Parameter) | ein leerer Ordner nur für diesen Test, z. B. um eine Testdatei zu schreiben |

Starten: `uv run pytest` im Ordner, der den Ordner `tests/` enthält. Mit `-v` siehst du jeden Test einzeln.

> **Warum Tests bei Agenten so wichtig sind:** Erinnerst du dich an die Fehlerakkumulation aus Skript 1.1? Tests sind die objektive Rückmeldung, die einen Agenten seine eigenen Fehler erkennen lässt. In Projekt «Forge» schreiben und starten Agenten selbst Tests. Dafür musst du wissen, wie gute Tests aussehen.

## 6. Ein kleines Kommandozeilen-Werkzeug

Für Aufgabe 1 baust du ein Programm, das man so aufruft:

```
uv run python -m loglens data/access.log --top 10 --out summary.json
```

Die Standardbibliothek bringt dafür `argparse` mit:

```python
import argparse

def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser(prog="loglens", description="Webserver-Logs auswerten")
    parser.add_argument("logfile", type=Path)
    parser.add_argument("--top", type=int, default=10)
    parser.add_argument("--out", type=Path)
    args = parser.parse_args(argv)
    ...
    return 0
```

Zwei Muster machen das Programm testbar:
- **`main(argv)` nimmt die Argumente als Liste.** Ein Test kann dann `main(["datei.log", "--top", "3"])` aufrufen, ohne die Kommandozeile zu brauchen.
- **`main` gibt einen Exit-Code zurück** (0 = gut, alles andere = Fehler), statt das Programm selbst zu beenden. Eine Datei `__main__.py` im Paket ruft `raise SystemExit(main())` auf. Dadurch funktioniert `python -m loglens`.

## 7. async/await: viele Dinge gleichzeitig

Netzwerkaufrufe verbringen fast ihre ganze Zeit mit Warten. Zwanzig Aufrufe à 0,5 Sekunden dauern nacheinander 10 Sekunden. Gleichzeitig dauern sie kaum länger als der langsamste einzelne.

```python
import asyncio
import httpx

async def fetch(client: httpx.AsyncClient, url: str) -> int:
    r = await client.get(url)          # await: hier darf ein anderer Aufruf weiterlaufen
    return r.status_code

async def main() -> None:
    urls = [f"https://example.org/?q={i}" for i in range(20)]
    async with httpx.AsyncClient(timeout=10.0) as client:
        results = await asyncio.gather(*(fetch(client, u) for u in urls))
    print(results)

asyncio.run(main())
```

Die Begriffe:

| Begriff | Bedeutung |
| --- | --- |
| `async def` | definiert eine **Coroutine**: eine Funktion, die unterwegs pausieren kann |
| `await` | «warte auf das Ergebnis und lass in der Zwischenzeit andere arbeiten» |
| `asyncio.run(main())` | startet die Ereignisschleife, die alle Coroutinen verwaltet |
| `asyncio.gather(...)` | startet mehrere Coroutinen gleichzeitig und sammelt die Ergebnisse |

**Nicht alles auf einmal: Rate-Limiting.** Hundert gleichzeitige Anfragen an einen fremden Dienst sind unhöflich und führen zu Sperren (Status 429 «Too Many Requests»). Ein `asyncio.Semaphore` begrenzt, wie viele gleichzeitig laufen:

```python
limit = asyncio.Semaphore(5)           # höchstens 5 gleichzeitig

async def polite_fetch(client, url):
    async with limit:
        return await client.get(url)
```

**Fehler dürfen den Rest nicht abreissen.** Mit `asyncio.gather(..., return_exceptions=True)` kommen Fehler als Ergebnis zurück, statt alles abzubrechen. Bei Agenten ist das Pflicht: Ein Tool, das ausfällt, darf nicht die ganze Aufgabe zum Absturz bringen. Der Agent soll den Fehler sehen und darauf reagieren.

**Höflich sein:** Viele öffentliche Dienste verlangen, dass sich Programme im `User-Agent`-Header ausweisen, etwa mit Name, Zweck und Kontakt. Wikimedia (Wikipedia) verlangt das ausdrücklich. Ohne aussagekräftigen User-Agent können Anfragen blockiert werden.

## 8. KI-generierten Code prüfen

In Aufgabe 2 lässt du den Cursor-Agenten dieselbe Aufgabe lösen. Der Code wird auf den ersten Blick gut aussehen. Prüfe ihn trotzdem wie den Code eines neuen Kollegen:

| Frage | Typischer Fehler von KI-Code |
| --- | --- |
| Laufen die vorgegebenen Tests? | Funktioniert für das Beispiel, scheitert an Randfällen |
| Werden Fehler behandelt oder verschluckt? | `except Exception: pass` |
| Stimmt das Verhalten mit der Vorgabe überein? | Eine Anforderung wurde still weggelassen oder «verbessert» |
| Gibt es erfundene Funktionen oder Parameter? | Halluzinierte API, z. B. eine Pydantic-Methode aus Version 1 |
| Ist es einfach genug? | Drei Abstraktionsschichten für 80 Zeilen Logik |
| Würdest du jede Zeile erklären können? | Wenn nicht: nicht übernehmen |

**Bessere Ergebnisse durch bessere Aufträge:** Gib dem Agenten die Anforderungen, die vorhandenen Tests und die Abnahmekriterien mit. Verlange, dass er die Tests ausführt, bevor er «fertig» meldet. Damit wendest du das Prinzip aus Skript 1.1 an: Rückmeldung durch Tests verbessert den Agenten.
